# Runbook

What to do when one of the platform's alerts fires. Every alert carries a `runbook` link to a section here:
`ErrorBudgetBurn` of a latency SLO → [latency](#latency), of any other SLO → [error-budget-burn](#error-budget-burn)
(or the section an SLO names with `runbook:` in its app.yaml — your own runbook), the regression's tickets →
[experiment-regression](#experiment-regression).

- **page**: users are affected now → act immediately.
- **ticket**: something is degrading, or a safety net is broken → fix within the working day.

Only prod clusters notify, and only from prod namespaces; on a lab cluster the alerts are the experiments' subject and
stay in Alertmanager ([concepts.md](concepts.md)).

## First five minutes (any alert)

1. **Which SLO, which environment?** The labels: `namespace` (`<app>-<env>`), `slo` (`<app>-<slo name>`),
   `severity`, `long` (the burn-rate window: `1h` fast, `6h` medium burn). The SLO's `description` in the app's
   `app.yaml` (also in Pyrra) says what counts as a bad event — and what it cannot see.
2. **Is it still burning?** Pyrra (`kubectl -n monitoring port-forward svc/pyrra-api 9099:9099`): the error budget
   left and the burn rate over time. Grafana (`svc/kps-grafana 3000:80`) for the application's own dashboards.
3. **What changed?** Argo CD (`kubectl -n argocd get applications`; history per Application) and `git log` of the
   instance repository: every deployment, promotion and configuration change is a commit there.
4. **Started right after a deployment? Roll back first, investigate second** ([Rollback](#rollback)).

## error-budget-burn

Alert: `ErrorBudgetBurn` (from the SLOs in `app.yaml`, generated by Pyrra).

| Severity | `long` | Burn | Meaning |
|---|---|---|---|
| page | 1h | fast: ≈ 14× the sustainable rate (over 1h and 5m) | at this rate the 28-day budget is gone in about 2 days |
| page | 6h | medium: ≈ 7× (over 6h and 30m) | gone in about 4 days; inhibited while the fast burn of the same SLO pages |
| ticket | 1d / 4d | slow | gone before the window ends; inhibited while the same SLO pages |

The alert resolves when the short window is clean again; the medium-burn page can follow a short, sharp outage by a
few minutes after recovery (the 6h window still remembers it) — check that the SLI is good now before digging.

What to look at depends on the SLO's SLI type (its key in `app.yaml`):

### availability

Bad events: requests the application itself counted as server errors (`errors` matchers, e.g. `code=~"5.."`). Client
errors (4xx) never count.

1. One route or all? One environment or several? `sum by (route, code) (rate(<metric>{namespace="<ns>"}[5m]))`.
2. Logs of the failing pods: `kubectl -n <ns> logs deploy/<name> --since=15m` (or the Rollout's pods).
3. Typical causes: a recent deployment → [Rollback](#rollback); a dependency down (database, another service) →
   that dependency's own SLOs and pods; resource exhaustion (`kubectl top pods -n <ns>`, OOMKilled in
   `kubectl -n <ns> get pods`).

**Its blind spot:** requests that never reach a pod (no ready pod, a broken Service) are counted nowhere. If users
complain and this SLO is quiet, look at the probe SLO.

### probe

Bad events: the blackbox prober (from outside the pods, every 15 s) did not get a 2xx in time.

- **probe burning, in-pod availability quiet**: requests do not reach a pod at all. `kubectl -n <ns> get
  pods,endpoints`: no ready pod (crash loop, failing readiness probe — e.g. a readiness check that depends on a
  database that is down), a Service whose selector matches nothing, a NetworkPolicy.
- **both burning**: the application answers with errors → [availability](#availability).
- **only the probe, and the app looks fine**: the prober itself (`kubectl -n monitoring logs
  deploy/blackbox-exporter`), or the probed path / URL changed (the `probe` block of the SLO).

### latency

Alert: `ErrorBudgetBurn` on a latency SLO (`slo="…-latency"`): too many requests slower than the SLO's
`threshold`. A latency SLO counts every request, failed ones included: requests hanging until a timeout burn it
together with the availability SLO.

1. Grafana / Prometheus: did latency rise with traffic (capacity) or at a deployment (regression)?
2. Regression → [Rollback](#rollback). (A canary analysis at low traffic can miss contention that only shows under
   load: that is what the canary's load test is for.)
3. Capacity: CPU throttling and memory (`kubectl top pods -n <ns>`), the slowest dependency (database, another
   service). Scale through Git (replicas in the overlay or values), never with `kubectl scale`: Argo CD's self-heal
   reverts it.

### age (freshness)

Bad: the metric (unix time of the last good run / processed item) is older than `max`. Something scheduled or
asynchronous stopped making progress.

1. The job or worker: `kubectl -n <ns> get cronjobs,jobs,pods` — the last Job's logs (`kubectl -n <ns> logs
   job/<name>`), a CronJob that is suspended or whose schedule never comes, a worker in crash loop.
2. A run that succeeded but did not update the metric: the exporter / Pushgateway / the code that sets it.
3. After the fix, run it once now: `kubectl -n <ns> create job --from=cronjob/<name> manual-$(date +%s)`.

### ratio

Bad events: `errors` among `total`, two counters the application exports — often an asynchronous pipeline (items
not processed in time among items created).

1. Is the backlog growing (nothing processes) or old (processing too slowly)? The application's own gauges for queue
   length and oldest item, if it has them.
2. The consumers: pods, crash loops (`kubectl -n <ns> logs <pod> --previous`), a recent release → [Rollback](#rollback).
3. Too slow: more replicas through Git; the dependency they wait on.
4. One item that fails forever (a poison message) holds the SLI down by itself: find and park it.

### bool

Bad: the 0/1 gauge the SLO watches is 0. The SLO's description names what it stands for (e.g. "WAL archiving keeps
up"); the component that sets the gauge has the details (its logs, its own status). Fix the cause, then check the
gauge returns to 1.

## SLOMetricAbsent

Ticket: the SLI's metric has no data at all, so the SLO is blind — it cannot burn, whatever happens. Its `runbook`
link is the SLO's own section above.

- No pod exports the metric: all down or never started (`kubectl -n <ns> get pods`), or Prometheus does not scrape
  them (the ServiceMonitor / PodMonitor: Prometheus → Status → Targets).
- The metric or a label was renamed in a release: compare the SLO's `metric` / `matchers` in `app.yaml` with
  `/metrics` of a pod.
- `age`: the job has never succeeded since the metric appeared — see [age](#age-freshness).
- `ratio`: an error counter that only appears at the first error is "absent", not zero: export both counters at 0
  from the start.

## experiment-regression

Tickets from the daily fault regression on lab clusters ([experiments.md](experiments.md)). Nobody's users are
affected; what is in doubt is whether the alerts would fire in a real outage.

### SLOExperimentFailed

The last run of `experiment` failed: an expected alert did not fire (in time), one that must stay quiet fired, an
unexpected page fired, or an alert did not resolve after the fault. Until it passes again, that SLO's alerting is not
verified.

1. The report: the regression records each result (ConfigMap `slo-experiments/experiment-results`, key
   `<experiment>.json`), and the last Job's log has the full run:
   `kubectl -n slo-experiments logs job/<last regression job>`. The ✗ lines say which prediction broke.
2. Reproduce by hand on the lab cluster: `python3 scripts/experiment.py --kubeconfig <lab kubeconfig>
   <instance>/apps/<app>/experiments/<experiment>.yaml`.
3. Decide which side is wrong:
   - **the alerting regressed** (an SLO, a metric, a label, a routing change, a release of the application): fix it
     — this is the outage you just did not have;
   - **the prediction was wrong** (e.g. the alert fires correctly but later than `within`, for a reason you accept):
     change the experiment, with the reason in the commit;
   - **the environment** (lab overloaded, images not pullable): fix the lab; a run whose time did not flow
     normally is INVALID, not FAIL, and does not raise this ticket.

### SLOExperimentRegressionStale

No scheduled regression has finished for 2 days: the lab was off or asleep, the CronJob does not run, the runner
crashed before recording, or the exporter is down.

1. `kubectl -n slo-experiments get cronjobs,jobs` — last schedule time, a suspended CronJob, Jobs that never
   started (`kubectl -n slo-experiments describe job <name>`).
2. The guard: the runner refuses unless every node carries `slo-platform/lab=true` (a new node without the label
   stops it): `kubectl get nodes -L slo-platform/lab`.
3. The exporter: `kubectl -n slo-experiments get pods`.
4. Run it once now: `kubectl -n slo-experiments create job --from=cronjob/experiment-regression manual-$(date +%s)`.

### SLOExperimentRegressionBroken

A regression Job failed (exit ≠ 0): the runner itself, not an experiment (failed experiments are
SLOExperimentFailed). Typical causes in its log (`kubectl -n slo-experiments logs job/<job_name>`): cloning the
product or the instance failed (a private repository and no or an expired token in `slo-experiments/git-credentials`
→ `tofu apply` with a fresh token), an experiment file that does not parse, the results ConfigMap not writable.
Delete the failed Job once understood; the alert clears with it.

## Canary aborted

Not an alert: `kubectl argo rollouts get rollout <name> -n <ns>` shows `Degraded` / `RolloutAborted` and the failing
analysis metric (error ratio, latency, the load test). Traffic is already back on the stable version. Fix forward, or
revert the commit that introduced the change; the Rollout returns to Healthy once its spec matches the stable version.

## Admission denied

Only with `optional.policies: true`. Argo CD shows `admission webhook … denied the request: Policy <name> failed:
<message>`; the message names the container and the missing setting (pinned image, resources, readiness probe,
non-root). Fix the manifest. The same policies run in CI on pull requests (`scripts/validate.sh`), so this normally
only hits objects created at runtime (operators, hooks).

## Rollback

Everything is a commit in the instance repository: `git revert <commit>` (the image tag bump or the configuration
change), push (through your review process). Argo CD syncs within about a minute. Never `kubectl edit / scale /
rollout undo`: self-heal reverts manual changes.
